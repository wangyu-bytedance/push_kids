## 固定发布模式

1. 先冻结发布范围，记录 Git commit、未提交差异、目标环境和发布版本；后端生成最小白名单发布目录
   和 SHA-256 manifest，禁止直接从活动仓库根目录上传。
2. 先执行自动检查；任何必需检查失败都停止发布，不得以“先上线再修复”替代。
3. 有数据库变更时，先完成兼容性审查和 Alembic migration，再发布兼容的新后端。只有未满足
   `BACKEND-RELEASE.md` §4.2 的纯增量兼容条件时，本次迁移前新增备份才是阻断门禁。
4. 后端先灰度并完成健康检查和业务 smoke；公网入口保持关闭。
5. 后端稳定后再上传小程序前端，先体验版真机验收，再提交微信审核。
6. 微信审核通过后由管理员人工发布正式版。
7. 保留上一不可变后端版本；按[数据库备份保留](#数据库备份保留)清理备份并记录结果。

## 数据库备份保留

每次发布后，完整列出数据库备份，按创建时间从新到旧保留最新3份；超过3份时，从最旧的开始
删除，直到剩3份。不足或等于3份时不删除。清理后重新核对数量，在发布记录中写明实际保留和
删除的备份及数量。

本规则由用户于2026-11-05确认，取代原成本审计草案中的保护集与观察窗口保留提案；
独立成本需求已[取消归档](../../specs/rejected/OPS-20261010-CLOUD-COST-RETENTION.md)。

## 发布状态记录的分类

2026-10-26开发归档口径：有匹配范围/源码的云端交付证据即可认定需求开发完成并将Spec置`DONE`归档；后端正常部署和小程序开发版成功上传分别作为对应端的交付阶段。验收缺项继续按实际结果独立记录，体验版/审核/正式发布仍保持原阶段，不因DONE自动推进。仅本地新增、preview、dry-run或失败版本不能据旧包归档；后续发布继续执行本手册门禁。依据为[用户批准的治理Spec](../../specs/completed/GOV-002-CLOUD-DELIVERY-DEVELOPMENT-COMPLETION.md)。

本目录记录每次发布实际到达的阶段和下一阶段需要复核的事项，不是代码问题或缺陷清单：

- “灰度不可变版本已创建、未全量切流”是后端发布范围事实；灰度发布本来就可以在该阶段结束。
- `NOT_RUN` 表示某项不在当次已执行证据内，供后续体验、提审或正式发布时复核；它本身不等于
  测试失败、代码缺陷或当前工作阻塞。
- `NOT_APPLICABLE` 表示按变更清单和 `SPEC-20261011-RISK-BASED-RELEASE-GATES-01` 判定门禁不触发；
  报告须写清不触发的范围与证据，不得把它记作测试 `PASS`。影响不明时按触发处理。
- “开发版本已上传、未设置体验版、未提交审核、未发布正式版”是微信平台版本状态，不应登记为
  issue 或 blocker。
- 只有当某次任务明确要求到达更后的发布阶段，或该阶段的必需检查实际失败时，才按相应发布门禁
  停止推进；这不改变历史发布记录的成功范围。

## 人工操作输出约定

自动化执行到必须由管理员完成的页面操作、扫码、验证码、隐私/法律声明、密钥配置或最终发布时，
立即停止在该门禁之前，并按下面格式直接输出：

```text
【需要人工操作】<操作标题>
原因：<为什么不能或不应自动完成>
操作入口：<可点击 URL>
导航路径：<控制台菜单路径>
需要填写/选择：
- <字段和值或判断标准>
完成标志：<页面上应出现的状态>
完成后回复：已完成 <操作标题>
```

约束：

- 不要求用户把密码、OpenID、数据库连接串、Ark Key、HMAC Key 或 COS 凭证发到聊天中。
- 表单涉及服务类目、隐私声明、备案、资质、发布范围等真实对外陈述时，只给建议和核对要求，
  由账号管理员确认并提交。
- “已上传”“体验版”“审核通过”“已发布”是不同状态，发布报告必须明确写出实际到达的状态。
- 不能操作某个受保护站点时，给出直达入口、菜单路径、字段建议和完成标志，不尝试绕过平台保护。
